Step 1.2

Branching, in isolation, before you need it

Practice the mechanics once on something trivial, so it's muscle memory by the time Part 2 uses it for real. Add a one-line README.md on a branch:

git switch -c docs/readme

Checkpoint: main now has the README, and the graph shows a clean, fast-forward merge — no conflict, because nothing else changed main in the meantime.

You'll do this exact sequence — switch -c, edit, add, commit, switch main, merge — repeatedly through Part 2 as real features land. A real merge conflict (two branches editing the same line) is coming in Step 2.9, once there's an actual UI to fight over.

Step 1.3

Push to GitHub

  1. Create a new empty repo on github.com (no README/.gitignore — you already have local history).
  2. git remote add origin https://github.com/YOUR-USERNAME/taskflow.git
git push -u origin main
Checkpoint: your commits are visible on GitHub. Keep this terminal open — every step in Part 2 ends with a commit here.

Golden rules: stage before you commit — git commit before git add commits nothing. Never force-push a shared branch — use git revert <id> to undo a shared mistake, not git reset. Small, focused, present-tense commits.

Step 2.2

The model

In tasks/models.py:

from django.db import models
from django.contrib.auth.models import User

class Task(models.Model):
    PRIORITY_CHOICES = [
        ("low", "Low"),
        ("medium", "Medium"),
        ("high", "High"),
    ]

    owner = models.ForeignKey(User, on_delete=models.CASCADE)
    title = models.CharField(max_length=200)
    priority = models.CharField(max_length=6, choices=PRIORITY_CHOICES, default="medium")
    due_date = models.DateField(null=True, blank=True)
    done = models.BooleanField(default=False)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.title

on_delete=models.CASCADE: deleting a user deletes their tasks too. choices= is how a dropdown's valid values get enforced server-side, not just offered client-side.

python manage.py migrate

Step 2.4

Views (function-based)

In tasks/views.py:

from django.contrib.auth.decorators import login_required
from django.shortcuts import render, redirect, get_object_or_404
from .models import Task

@login_required
def task_list(request):
    if request.method == "POST":
        title = request.POST.get("title", "").strip()
        priority = request.POST.get("priority", "medium")
        due_date = request.POST.get("due_date") or None
        if title:
            Task.objects.create(owner=request.user, title=title, priority=priority, due_date=due_date)
        return redirect("task_list")

    tasks = Task.objects.filter(owner=request.user).order_by("-created_at")
    return render(request, "tasks/task_list.html", {"tasks": tasks})

@login_required
def toggle_task(request, task_id):
    task = get_object_or_404(Task, id=task_id, owner=request.user)
    task.done = not task.done
    task.save()
    return redirect("task_list")

@login_required
def delete_task(request, task_id):
    task = get_object_or_404(Task, id=task_id, owner=request.user)
    task.delete()
    return redirect("task_list")

@login_required sends anonymous visitors to the login page. get_object_or_404(..., owner=request.user) stops one logged-in user from toggling or deleting another user's task by guessing an ID in the URL — every query and every create is scoped to request.user, never trust an ID alone.

git commit -m "Add task_list, toggle_task, delete_task views"

Step 2.8

JavaScript — dark mode toggle

Everything else in this app is server-rendered on purpose (Step 2.4's callout explains why), but a theme preference belongs to the browser, not the database — a good, honest reason to reach for a little vanilla JS instead of a round trip to Django. This covers the DOM, event listeners, and localStorage in one small, real example.

Add the button to the header in task_list.html:

<header class="app-header">
  <h1>📋 TaskFlow — {{ user.username }}</h1>
  <div>
    <button id="theme-btn" type="button">🌙 Dark mode</button>
    <form method="post" action="{% url 'logout' %}" style="display:contents">
      {% csrf_token %}
      <button type="submit" class="btn">Log out</button>
    </form>
  </div>
</header>

Then add this <script> just before </body>>:

<script>
  const themeBtn = document.getElementById("theme-btn");
  function applyTheme(theme) {
    document.documentElement.dataset.theme = theme;
    themeBtn.textContent = theme === "dark" ? "☀️ Light mode" : "🌙 Dark mode";
    localStorage.setItem("taskflow.theme", theme);
  }
  themeBtn.addEventListener("click", () => {
    const next = document.documentElement.dataset.theme === "dark" ? "light" : "dark";
    applyTheme(next);
  });
  applyTheme(localStorage.getItem("taskflow.theme") || "light");
</script>

document.documentElement is the <html> tag — setting .dataset.theme on it sets data-theme="dark", which is exactly the attribute selector the CSS in Step 2.7 is waiting for. localStorage persists the choice per-browser, so it survives a refresh even though nothing was saved to the database.

Checkpoint: click the button — the whole page re-skins instantly, no page reload. Refresh the page — it's still dark.

Level 3.0

Sanity check Docker itself

docker run -d -p 8080:80 nginx:alpine

docker ps
docker rm -f <container-id-or-name>

Level 3.1

requirements.txt and a Dockerfile

From inside taskflow-backend/ (the folder with manage.py):

pip freeze > requirements.txt
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000

CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]

Read the order before you type it: requirements.txt is copied and installed before the rest of the code. That's deliberate layer ordering — editing a .py file later and rebuilding reuses the cached pip install layer instead of reinstalling everything. Reverse the two COPY lines and every rebuild gets slow.

CMD is the default command — anyone running docker run can override it. ENTRYPOINT would pin the image to always run as one program no matter what.

# .dockerignore
venv/
__pycache__/
*.pyc
db.sqlite3
.env
.git/
docker build -t taskflow:v1 .
docker run -d -p 8000:8000 --name taskflow-app taskflow:v1
Checkpoint: http://localhost:8000 serves the app — this is runserver running inside a container, not on your machine directly.

Level 3.2

Migrations and persistence

docker exec -it taskflow-app python manage.py migrate
docker exec -it taskflow-app python manage.py createsuperuser

Right now, docker rm -f taskflow-app deletes the database forever — it only lived in the dead container's writable layer. Fix that with a named volume:

docker rm -f taskflow-app
docker run -d -p 8000:8000 -v taskflow-data:/app --name taskflow-app taskflow:v1
docker exec -it taskflow-app python manage.py migrate
Checkpoint: add a task, docker rm -f taskflow-app, re-run the same -v taskflow-data:/app command — the task is still there.

Level 3.3

Postgres via Docker Compose

A single container is fine for one service; two services (web + database) that need to talk to each other is what Compose is for.

pip install "psycopg[binary]"
pip freeze > requirements.txt

In taskflow/settings.py:

import os

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ.get("POSTGRES_DB", "taskflow"),
        "USER": os.environ.get("POSTGRES_USER", "taskflow"),
        "PASSWORD": os.environ.get("POSTGRES_PASSWORD", "taskflow"),
        "HOST": os.environ.get("POSTGRES_HOST", "db"),
        "PORT": "5432",
    }
}

HOST defaults to "db" — inside a Compose network, containers reach each other by service name, never localhost.

# .env — add to .gitignore and .dockerignore, never commit real credentials
POSTGRES_DB=taskflow
POSTGRES_USER=taskflow
POSTGRES_PASSWORD=changeme
# compose.yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER}"]
      interval: 5s
      timeout: 3s
      retries: 5

  web:
    build: .
    command: python manage.py runserver 0.0.0.0:8000
    ports:
      - "8000:8000"
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_HOST: db
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - .:/app

volumes:
  pgdata:

depends_on: condition: service_healthy — without the healthcheck, depends_on only waits for the db container to start, not for Postgres to be ready, and the first migration would race it and fail.

docker compose up --build
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
Checkpoint: docker compose down then docker compose up again (no -v) — tasks and superuser survive, since they live in the pgdata volume, not either container.
docker compose down -v   # full teardown
git add .
git commit -m "Containerise TaskFlow: Dockerfile, compose, Postgres"
git push

Explain it

🧠 What you should be able to explain afterward

  • The difference between an image (the recipe) and a container (a running instance of it)
  • Why COPY requirements.txt . happens before COPY . .
  • Why a volume, not the container's own filesystem, is what makes data survive docker rm
  • Why services in Compose talk to each other by service name, never localhost
  • Why .env never gets committed, and where the values end up at runtime
